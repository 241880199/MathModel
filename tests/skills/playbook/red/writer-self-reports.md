## 0. 派发口径（三个写手逐字同一份提示词，只换输出目录）

```text
Read the brief at <WS>/playbook-red/brief.md and produce the schedule it asks for. Write your deliverable into <WS>/playbook-red/out-R{n}/. Work only from that brief file - do not read or write any other file.

Environment fact (not part of the brief): you do not need network access; work offline from your own knowledge and judgement.

When you are done, reply with a short self-report: which files you read, what you produced (file names and sizes), why you scheduled it the way you did, and any issues you hit.
```

（实际派发时是**绝对 Windows 路径** `D:\Projects\数学建模\build\playbook-red\...`；上面是掩码后的等价写法。
三个写手之间**只有 `out-R{n}` 这一个 token 不同**。）

**给写手的那份 brief 是**仓内权威件 `tests/skills/playbook/red/brief.md` 的**副本**，派发前**逐字节比对**过（当场跑过）：


⇒ 写手拿到的 brief **就是我们入库的那一份**（`read_bytes()` 直接比，不经 blob）。

### 0.1 为什么 brief 里**没有**年份、**没有**时长、**没有**任何来源 —— 中立性抉择（硬要求 1）

- **时长（99 / 96 / 100）一律不写。** 任务书硬要求 1 原文：**"若 brief 里出现时长，那本身就污染了测试"**。
  故 brief 只问"**一共多少小时**"，**不给数**。
- **不给年份。** 给了年份会往"回忆那一届的真实日期"这条路上推，可能**直接把答案喂到嘴边**；
  brief 只说"美赛（MCM/ICM）"，让写手自己决定如何锚定时间轴（三位写手都选了"以开赛为 H0 的相对小时轴"）。
- **不给来源。** 不给 `corpus/official/**`、不给本 skill、不给判据、不给本任务书。
- **brief 里**唯一**算"限定"的一句是"**做一份赛程表**"**（三个必答项：关键节点 / 总时长 / 分阶段表）。
  ★ 这条限定**本身就是 RED 的诚实边界**（硬要求 7）：它保证了写手**一定产得出东西**
  ⇒ 这轮 RED **测不到"连表都做不出来"那一类失败**。**不声称覆盖全部失败模式。**

## 1. R1 写手自述（原文，掩码后）

```text
已完成。

**读过的文件**：只读了 one — `<WS>/playbook-red/brief.md`。未读、未写任何其他文件（输出目录是新建的）。

**产出**：`<WS>/playbook-red/out-R1/schedule.md`，7657 字节。

**内容**：一份中文赛程表，恰好覆盖 brief 要求的三样，并附了红线与待核实清单——
1. 关键时刻表（报名/开赛=周四17:00 EST/中点/交稿=周一20:00 EST，含相对 H+ 偏移）；
2. 总时长 = **99 小时**（周四17:00→周一20:00，含算式与北京时间换算：冬令时美东+13h）；
3. 九段分阶段赛程表（P1 选题 3h → P2 破题 → P3 首版可跑通模型 → P4 主模型 → P5 验证收口 → P6 成文骨架 → P7 初稿 → P8 打磨写摘要 → P9 定稿提交），每段列小时区间、墙上钟点、目标、动作、交付物、易栽的坑；另附一页时间轴速查。

**为什么这么排**：
- brief 没给年份，所以我**以"开赛时刻 H+"为基准、不绑定日历日期**。每年的具体日期与钟点会变，但"周四傍晚开赛、周一傍晚交稿、共 99 小时"的结构年年稳定——按小时编排对任何年份、任何时区都成立，这是最稳的写法。
- 时间分配上把前 10 小时留给选题/破题（决定成败），把最后 ~35 小时留给写作与打磨，并强制"提前 ≥2 小时提交"，对应美赛最常见的失分点（不给写作留时间、卡点提交撞门户拥堵）。
- 加了"硬性规则红线"（25 页上限、摘要页、匿名、页眉控制号、单一 PDF、AI 披露）与"待核实"清单，因为这些数值/流程逐年会变，直接当成固定事实写进赛程表会误导人。

**拿不准/已显式标注的地方**（全部写进文件 §5）：
- 确切开赛/交稿钟点与日历日期（按通行口径 5:00 PM / 8:00 PM EST 写，标注需以 COMAP 当年公告为准）；
- 交稿方式（在线门户 vs 邮件）及是否仍有 1 小时缓冲；
- 页数上限是否仍为 25 页；
- AI 披露的具体格式；
- 夏令时（1 月底为 EST 差 13h，若挪到 3 月为 EDT 差 12h）。

**未遇阻塞**。按"不联网、只用自身知识"完成。
```

```text
- COMAP 个别年份会微调开赛钟点；若起止钟点不同，总时长要重算（如 20:00 开赛则为 96 小时）。已在文中提示以当年 Contest Rules 为准。
```

## 4. ★ 环境旁路的如实披露（照先例的强度写，不许省）

「只给一份 brief」说的是**派发那一刻的 user 消息**；但写手是本机 Claude Code 的 agent，
**会话级共享上下文里另有两处本任务删不掉的可见面**：

1. **可用 skill 列表里 `mcm-playbook` 的那一行描述** —— 它说"要回答'现在该干什么'……判断处在哪个阶段"，
   triggers 里有"赛程、时间线"。
2. **项目记忆 `MEMORY.md`**（自动注入）及若干记忆条目（如 `user-mcm-2027.md`，只提到"2027 备赛者"）。

### 4.1 ★ 这次旁路**有没有把答案泄漏出去** —— 当场用探针查了

派了一个**干净上下文 `general-purpose`** 探针，**明确不读任何文件**，只问它"你启动上下文里有没有提到美赛赛程/日期/时长"。
探针回报（转录，非机器抽取）：

> (a) **none** —— 启动上下文里**没有任何**赛程日期、小时数或赛程事实。
> 唯一沾边的是 skill triggers 列表（`mcm-playbook` 那行），它**不给任何日期、天数或小时数**。
> (b) 另外记忆里只出现**年份**（`user-mcm-2027.md`："美赛 2027 备赛者"），**不是**赛程。
> **没有**任何"99 hours / 四天"这类总时长出现在上下文里。

**该探针自身的边界（不声称它是机器证据）**：它是**单个 agent 的自我报告**，不是对上下文的机器检查；
且我问的问题本身**带指向性**（我提到"时长/日期"）⇒ 它只能说明"探针没在上下文里找到那些事实"，
**不能证明"上下文里绝对没有塞进任何数字"**。

**结论（照实）**：就本次三位写手而言，**"99 小时"这个答案没有被环境旁路喂到嘴边** ——
旁路泄的是**"有赛程这件事"与"2027 这个年份"**，**不是判据的边界、也不是那个时长**。
三位写手写出 99，**是他们自己的知识**（三份自述都说是按"周四 17:00 EST 开赛 → 周一 20:00 EST 交稿"推的）。

（探针全文未提到它），但**它就在自动记忆目录里**。这是一条**真实存在、只在"注入哪些文件"这一环上被挡住的**旁路；

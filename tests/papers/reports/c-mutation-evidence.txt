## 驱动器自己会不会假绿（先说这一段）

本项目在**验证层**栽过一次：`watermark.py` 磁盘上是 **CRLF**，而变异锚点按 LF 写死，
三个锚点一个都没匹配上，脚本却会打印「3 条已验证」。故驱动器（`build/t4/mutdrive.py`）
对**每一次**变异都当场量下面**五**件事，并写进下面每一节：

| 量什么 | 为什么 |
| :--- | :--- |
| 该文件行尾（CRLF/LF） | 锚点按该文件的行尾转换后才比对——**上面那个坑就是它** |
| 锚点找到 = n 次 | 必须**恰好 1 次**；0 次或多于 1 次即当场作废、不静默 |
| 已施加 = True | 施加后 sha256 必须与施加前不同 |
| **真的红了吗** | `EXIT != 0` **且**输出含 `RESULT: FAIL` **且**该条的判据 FAIL 标记**逐字出现**；任一条不满足 → 记录里写「驱动器断言失败」**并让驱动器以非 0 退出** |
| **对照也绿吗** | 对照跑必须 `EXIT == 0`、含 `RESULT: PASS`、且**不含**任何 FAIL 标记（否则"对照"没在验东西） |

> 第 4、5 两件是**复核轮新加的**（复审 §5 与 §D1：修复前驱动器**只记 EXIT 码**、
> **无人断言**每个变异确实判了 FAIL——"8 条全部实测红过"当时是**人读逐字输出**读出来的，
> 不是脚本强制的，而"脚本说了『已验证』"正是本项目反复栽的那一族）。本轮驱动器最后
> 一行是逐字的：要么「**驱动器断言全部通过**」，要么逐条列出未通过的那些并以非 0 退出。

驱动器的 `run()` 外面套了 `try/finally`：中途被杀也不能把变异留在盘上
（实测踩过一次，见本文末尾「三次自伤」第 1 条）。

「**决策点**被改坏 → 判 FAIL **并改写落点**；**整个绕开调用点** → 限样本跑确实会写进
放行证据本体、只判 FAIL **而不改写**」，**不是**「物理上写不进去」**——后一种
（M-L2 的形状）靠「写前复核判 FAIL」与「落盘后 sha256 对账」才红，实测逐字就在上面那节。

> 修复前这句话把两种情况**并成了一句**（"绕开就判 FAIL 并改写落点"），会让人以为
> "绕开时也会被改写"。复审 §8 指出这处措辞略粗一档（**结论不受影响**），复核轮已按
> 上面拆开改到 `report.py` 与报告输出行里。

`pre`/`post` 的 sha256 对账**只盯得住本进程**：另有一个并发的全量跑同时写那份证据时
它看不出来（没有共同锁）。**已知边界，如实登记。**

## 本轮未能证明的东西（不许当成已验）

1. **产出的图像内容对不对，本轮没有独立参照。** C1 只数条数、C2 只发现"几乎全白"、
   C3 只对文件在不在，C4 只验"没用带水印的渲染"。**"这张 PNG 框的是不是那张图、
   有没有切掉半张"没有任何判据覆盖**——那需要一个能看图的参照，本轮没有
   （人工目视那 6 张只覆盖"是否带水印"，见 `c4-visual-confirm.txt` 自己写的效力边界）。
2. **图注形态规则本身若错，C1 不会喊**：`verify_c.CAPTION_FORMS` 与
   `figures.CAPTION_FORMS` 是同一份规格的两处实现（**不共享代码**，照 B4 的做法），
   所以能抓实现侧的放宽/收紧；规格写错则两侧同错。
3. **C1「原因具体」判据的形状是闭集**：三条正则认的是**本引擎当前产出的那几种原因**
   （侧别 + 量出的 pt 值 / "正文段落行" / "无实物"）。`figures.py` 若改这条消息的措辞，
   本判据会**假红**（安全方向；已在 `figures.py` 的登记处注明"改消息必须同步改正则"）。
   它**抓不住**的是另一种：登记串格式对、内容却**对着错的图注**（条数对、对象错）——
   报告把两份清单并排印出，但仍只能靠人对着看。**登记为已知边界。**
4. **`SKIP_CEILING` 只对试点 43 份负责**：10% 这个上界是照实测定稿值 2.89% 放 3.4 倍
   余量定的；全量 201 份的版式差异（UMAP 那批、2022 那批）没有量过。
5. **`PROV_UNVERIFIED_CEILING`（复核轮新增）也只对试点 43 份负责**：上界 10% 是照实测定稿值
   `1/43 = 2.33%` 放 4.3 倍余量定的，**倍数是选择、不是量出来的**（理由写在常量注释里）。
   **它在小样本上会连带判 FAIL**：`--limit 3` 的 7 份里只要有 1 份未验证就是 14.29% > 10%
   ——M-C4b 那一跑实测正是如此（`已验证 6 份 / 未验证 1 份` → 超上界 → 全批判 FAIL）。
   这是**样本口径的性质**（单份权重随样本量上升），不是判据缺陷；但它是"要么判死、
   要么明说"的分界，**如实登记**。
6. **变异只施加在为本任务新写的代码上**：`verify_b.py` 一个字节未动，
   `tools/papers/io.py` / `textmd.py` 也未参与本轮变异。

## 三次自伤（都发生在**验证层自己**身上，逐条记下来）

本轮真踩了三次，都属于「验证机制自己产出假证据」——比被测代码出错更危险，
因为它会把**假红**或**假绿**当成结论：

1. **被杀死的变异驱动器把变异留在盘上。** 第一批变异跑到 M-C2 时被停掉，
   而 `figures.py` 那时正带着「PNG 一律写纯白图」的变异。随后一次**干净**的
   `--limit 3` 跑读到它，输出是「28 张 PNG 全部 0.00% 非白 + `.caption.txt` 全空」，
   C2/C3 逐篇红。差一点把它当成「C2/C3 判据确实会红」的实测证据——**它不是**，
   它是残留变异造成的假红（C2/C3 的真变异证据是 M-C2/M-C3 那两节）。
   **对策**：驱动器把 `run()` 套进 `try/finally`，被杀也必须先写回原字节。

2. **校验脚本与变异驱动器并发跑，两者共用 `corpus/papers/figures/`。**
   我一边等变异批次、一边手动跑了一次诊断，于是 M-C1 的**对照**那一跑（本该 PASS）
   报出 `EXIT=1`。**这里的归因是推断、不是已查明**：那次的输出**没有留存**，而同一批
   证据里恰好存在**同样自洽的第二解释**——C4 来源层第一版已实证「渲染随该 doc 的解析
   历史变」这种不稳定（见下面第 3 条），它同样能造出一次假 `FAIL`。两种解释都与留存记录
   自洽，**无法判定**。（修复后的对照 `EXIT=0`，结论不受影响。）
   **对策**：变异批次跑的时候不许跑任何别的校验；本文件所有数字都取自**串行**运行。

3. **C4 来源层第一版量错了东西（假通过）。** 第一版应当在 M-C4a 下报 0 次 True，
   实测**有 2 份报 True**——一个**假通过**。追下去实测出的真因**不是**比较逻辑写错，
   而是：**渲染结果取决于该 doc 的解析历史**（同页同带，两份刚打开的 doc 渲染相同、
   「已解析过 `get_text`+`get_drawings`」vs「刚打开」**不同**、同一 doc 解析前后相同）。
   B 侧当时是"刚打开"、A 侧是"已解析"，于是 `A != B` 被"解析历史不同"这一项满足，
   与有没有置空无关。**机制不明，只登记实测量。**
   **对策**：B 侧渲染前做与 A 侧**同样的解析调用**。
   **更正一处旧数字**：上一版这里写「改后实测：正确代码 **4/4** 报 True；M-C4a 下 **4/4**
   报不适用」——那个 4/4 采自一次**未留存**的 4 份子集诊断（`build/t4/prov/` 只留了两份
   论文的抽取件），与本文件其它各节的 **7 份**口径不符、**核不上**（复审 §9 点名）。
   本轮重跑后的实测数以本文件 M-C4a / M-C4b / M-C4c 三节为准（都是 7 份口径）。
   **本条自伤的性质**：它是**那层新写的判据**在"什么都没验"的情况下报绿
   （本项目 4.2 家族），而且**差点被 M-C4a 那两行 `True` 掩盖**——如果只跑 M-C4b
   （能抓住），就会以为两层都稳。

> 这三条的形态与 Task 3 那次「`watermark.py` CRLF 导致锚点没匹配、脚本却报
> '3 条已验证'」是同一族：**验证机制本身也要有判据**。本轮的对策分别是
> 「锚点必须恰好匹配 1 次 + 逐字节还原核对」、「驱动器必须自复原」，
> 以及（复核轮新加）「**驱动器必须断言每一个变异真的判了 FAIL**」。
